# book-ocr 出力の「iPhone で音声読み上げ」対応 — 要求分析 (2026-07-28)

- 作成日: 2026-07-28
- 状態: 歴史的ドラフト。第一手として推奨した EPUB3 出力は v0.4.0 の `book-epub` として実装済み（2026-07-29）。TTS による M4B 生成と読み上げ用テキスト正規化は未着手（2026-10-11 に未マージのブランチから回収して保存）
- 対象: `book-ocr` の出力形式および読書体験
- 前提リポジトリ状態: `v0.3.0` / `book-ocr` は `index.json` + `<book>.md` + `pages/page_NNN.md` を出力

## 0. 結論 (TL;DR)

- **markdown が不便なのは「ファイル形式」だけの問題ではない。3 層に分けて考える必要がある** — (1) iPhone に届ける層、(2) 再生体験の層、(3) 読み上げに耐えるテキスト品質の層。形式変換だけをやると (3) が残って「聞けるが聞くに堪えない」になる
- **第一手は EPUB3 出力 (`book-epub`) を推奨**。Send to Kindle 経由で iOS Kindle アプリに戻せば、**現在リフロー型書籍でやっている操作体験をそのまま再利用**でき、学習コストがゼロ。実装コストも最小（追加依存ほぼなし、zip + XHTML）。副次的に「PDF が 100 MB 超で Claude Code に渡せない」問題の別解にもなる
- **「ながら聞き（画面 OFF・バックグラウンド・AirPods）」が本命ニーズなら、TTS による M4B オーディオブック生成が別途必要**。画面読み上げは原理的に画面を点けたままにする必要があり、EPUB 化では解消しない。ただし生成時間・コスト・外部 API への全文送信という新しい論点を持ち込む
- **どちらを選んでも「読み上げ用テキスト正規化」レイヤは共通で必要**。ページ跨ぎの文の再結合、markdown 記法の除去、ルビ／柱／ノンブルのノイズ除去。ここが実は本質的な作業量
- **優先度は §8 の検証 V-1（画面読み上げはロック中に継続するか）で分岐する**。決め打ちせず、先に 30 分の実機検証を推奨

## 1. 背景

### 1.1 現状 (as-is)

```text
Kindle.app (Mac)
  └─ kindle-cap ──► output/<book>/page_NNN.png  ──► output/<book>.pdf   （視覚確認用・100 MB〜1 GB）
                          └─ book-ocr ──► index.json
                                          <book>.md          （全文連結・grep 用）
                                          pages/page_NNN.md  （ページ単位）
```

`book-ocr` の出力は「Claude Code に読ませる」ことを主目的に設計されている（[`docs/ai-readability/2026-05-20.md`](../ai-readability/2026-05-20.md)）。実際その用途では PDF の 1/500 のサイズで完全に機能しており、目的は達成されている。

### 1.2 きっかけとなった不便

一方で、ユーザーの実際の読書行動はもう一つある:

> リフロー型の Kindle 書籍は、iOS の Kindle アプリ + 画面読み上げで音声として消費している。

つまり **「読む」ではなく「聞く」が主要な読書チャネルになっている**。ところが `kindle-cap` → `book-ocr` を通した書籍（＝固定レイアウトなど、そのままでは Kindle の読み上げが効かない書籍）は markdown で Mac 上に落ちるだけで、この「聞く」チャネルに合流できない。

ここに **パイプラインの断絶** がある。皮肉なことに、`kindle-cap` を使う動機になる書籍（固定レイアウト・自炊相当）こそ、読み上げが効かなくて困っている書籍のはずである。

> [!NOTE]
> この断絶は「markdown が読めない」ではなく「**markdown が読書導線に乗らない**」という問題である。形式の議論に入る前に、乗せたい導線が何なのかを分解する（§2）。

## 2. 現行体験の分解 — 「リフロー型 Kindle × 画面読み上げ」の何が価値か

移行先を評価するには、まず今の体験のどの属性を失いたくないのかを明示する必要がある。

| # | 属性 | 内容 | 重要度（推定） |
|---|---|---|---|
| E1 | ゼロ導線 | 買った本が勝手にライブラリに並ぶ。転送作業がない | 高 |
| E2 | 単一アプリ | Kindle アプリだけで完結。アプリを行き来しない | 高 |
| E3 | 位置の保持 | 中断しても続きから。デバイス間同期（Whispersync） | 高 |
| E4 | 速度調整 | 読み上げ速度を変えられる | 中 |
| E5 | 目と耳の切替 | 同じ本を、聞くのをやめてその場から目で読める | 中〜高 |
| E6 | 検索・ハイライト | 語句検索、ハイライト、メモ | 中 |
| E7 | 章移動 | 目次から飛べる、章単位で頭出しできる | 中 |
| E8 | 画面 OFF 継続 | 画面を消して・ポケットに入れて聞き続けられる | **要検証（§8 V-1）** |

E8 は現行体験で **達成できていない可能性が高い**（iOS の「画面の読み上げ」は画面表示を前提とする機能であり、ロック時の挙動は要確認）。もし現状 E8 が満たされていないなら、それは「現行体験の再現」ではなく「**現行体験の不満点**」であり、新しい体験を設計する（＝オーディオブック化する）強い動機になる。

**この 1 点が本要求分析の最大の分岐点**なので、§8 で最優先の検証項目として扱う。

## 3. 課題分析 — なぜ markdown のままでは代替できないか

課題を 3 層に分けて整理する。**形式変換で解ける層とそうでない層があり、これを混同すると「EPUB にしたのに使えない」になる**。

### 3.1 到達層 — iPhone に届かない

| ID | 課題 | 補足 |
|---|---|---|
| P1-1 | Mac → iPhone の転送が手動 | AirDrop / iCloud Drive / Send to Kindle いずれも現状は手作業 |
| P1-2 | iOS に markdown の標準リーダーがない | ファイルアプリでプレビューはできるが、読書 UI ではない |
| P1-3 | 書籍としてのメタデータがない | タイトル・著者・言語が付かず、ライブラリに整理されない |

### 3.2 再生体験層 — 聞く体験として成立しない

| ID | 課題 | 影響する属性 |
|---|---|---|
| P2-1 | 章構造・目次がない（`<!-- page:NNN -->` のみ） | E7 |
| P2-2 | 位置の保持がない。中断したら自力で探す | E3 |
| P2-3 | 画面 OFF・バックグラウンド再生ができない | E8 |
| P2-4 | 「1 ファイル 14 万字」を読み上げ機能に食わせる形になり、頭出しが困難 | E7, E3 |

### 3.3 テキスト品質層 — 目で読めるが耳では破綻する

**ここが最も見落とされやすく、かつ最も作業量が多い。** 目で読むテキストは飛ばし読み・読み返しで欠陥を補正できるが、耳で聞くテキストは線形にしか消費できないため、同じ欠陥が致命傷になる。

| ID | 課題 | 耳で聞いたときに何が起きるか |
|---|---|---|
| P3-1 | **ページ跨ぎの文の分断** | キャプチャ単位が画面なので、文が高確率でページ境界で切れる。読み上げが文の途中で不自然に間を空け、意味の切れ目を誤認させる |
| P3-2 | **markdown 記法がそのまま読まれる** | `#`, `|`, `---`, `![...](...)` が記号として発話される、あるいは無音の異物になる |
| P3-3 | **表・数式・コードブロック** | 表を線形に読み上げても情報にならない。「表は省略」等の方針決定が必要 |
| P3-4 | **ルビの二重読み** | OCR がルビを本文にインライン展開していると「漢字かんじ」のように二重に読まれる |
| P3-5 | **柱・ノンブル・脚注番号** | `--ignore_meta` で軽減済みだが、固定レイアウト本では取りこぼしが残る。章題が段落の途中に挟まる |
| P3-6 | **OCR 誤字** | 目なら文脈で補正できる誤字が、音声では意味不明な語として素通りする |
| P3-7 | **図表キャプション・図中文字** | 本文と区別されず流れ込む |
| P3-8 | **読みの曖昧性** | 「行った」「一日」「代替」等の同形異音語、専門用語・固有名詞の誤読。TTS 品質に直結 |

> [!IMPORTANT]
> P3-1 と P3-2 は**どの出力形式を選んでも必ず通る**。EPUB でも M4B でも同じ前処理が要る。したがって「読み上げ用テキスト正規化」は形式選択と独立した必須コンポーネントであり、**共通の中間層として設計すべき**（§7）。

## 4. 要求の抽出

### 4.1 ユーザー要求 (UR)

| ID | 要求 | 優先度 |
|---|---|---|
| UR-1 | `kindle-cap` で取り込んだ書籍を、iPhone で音声として消費できる | Must |
| UR-2 | 既存の読書体験（アプリ・操作）をできるだけ変えたくない | Should |
| UR-3 | 中断・再開ができ、位置を失わない | Must |
| UR-4 | 現行の `kindle-cap … && book-ocr …` 放置運用を壊さない。手作業を増やさない | Must |
| UR-5 | 聞いていて意味が取れる程度のテキスト品質がある | Must |
| UR-6 | 「聞く」だけでなく「目で読む」「grep する」用途も同時に維持される | Should |
| UR-7 | 章単位で頭出しできる | Should |
| UR-8 | 通勤・家事などの「ながら聞き」（画面を見ない）ができる | **要確認**（§8 V-1 次第で Must 昇格） |

### 4.2 機能要求 (FR)

出力形式まわり:

| ID | 要求 | 対応する UR |
|---|---|---|
| FR-1 | iOS の標準的な読書アプリで開ける電子書籍形式（EPUB3）を出力する | UR-1, UR-2 |
| FR-2 | 出力にタイトル・著者・言語 (`ja`) のメタデータを付与する | UR-1, UR-3 |
| FR-3 | 目次（`nav`）と、章／セクション単位のファイル分割を持つ | UR-7 |
| FR-4 | 既存の markdown / `index.json` / PDF 出力は変更せず維持する | UR-6 |
| FR-5 | 既存の `output/<book>/` を入力として**再 OCR なしに**変換できる（`kindle-cap-pdf` と同じ思想） | UR-4 |

テキスト正規化まわり:

| ID | 要求 |
|---|---|
| FR-6 | ページ境界で分断された文を再結合する（前ページ末尾が句点等で終わらない場合に連結） |
| FR-7 | markdown 記法を読み上げに適した表現へ変換または除去する |
| FR-8 | 表・画像参照・コードブロックの扱いを方針として選択できる（読み飛ばす／要旨を差し込む） |
| FR-9 | 柱・ノンブル等の残存ノイズを除去する |
| FR-10 | 正規化結果を人が確認・修正できる中間ファイルとして残す |

音声化まわり（Phase 3 相当）:

| ID | 要求 |
|---|---|
| FR-11 | 正規化テキストから音声ファイルを生成する |
| FR-12 | 章単位のチャプターを持つ単一ファイル（M4B）にまとめる |
| FR-13 | 生成を中断・再開できる（章単位のスキップ。`--skip-existing` と同じ思想） |
| FR-14 | TTS エンジンを差し替えられる（ローカル `say` / 外部 API）。`OCREngine` Protocol と同じパターン |
| FR-15 | 固有名詞・専門用語の読み辞書を外部ファイルで与えられる |

### 4.3 非機能要求 (NFR)

| ID | 要求 | 根拠 |
|---|---|---|
| NFR-1 | 追加依存は最小限。EPUB 出力は標準ライブラリ（`zipfile`）で実装可能な範囲に収める | `ocr` extra が既に約 1.5 GB。これ以上重くしたくない |
| NFR-2 | 音声生成のデフォルトは**ローカル完結・オフライン**とする | プライバシーと §10 の方針 |
| NFR-3 | 外部 TTS API の利用は明示的な opt-in とし、書籍全文が外部送信されることを実行時に警告する | §10 |
| NFR-4 | 長時間処理には進捗表示（`tqdm`）と再開手段を持たせる | OCR が既に 200p ≒ 1 時間。既存の `--progress` / `--skip-existing` と一貫させる |
| NFR-5 | ディスク容量の preflight を行う | 既存 `book_ocr/preflight.py` を踏襲 |
| NFR-6 | `mypy --strict` / `ruff` を通し、純粋関数を切り出してテスト可能にする | CONTRIBUTING の方針 |
| NFR-7 | EPUB は横書き（`writing-mode` 指定なし）を既定とする | 読み上げ用途では縦書き指定は無意味かつリーダー互換性を下げる |

### 4.4 非ゴール（YAGNI）

- DRM 回避・暗号化解除（README の方針どおり、対象外）
- 音声とテキストの同期ハイライト（EPUB3 Media Overlays）→ §5.4 で棄却
- 本文の自動翻訳・要約の本体機能化（別軸。§11 の将来候補に留める）
- Android / Windows 対応
- 電子書籍ストアへの配布を想定した EPUB 検証（`epubcheck` 完全準拠）。**個人利用の入力として通れば十分**
- 縦書き表示の再現

## 5. 解決候補

### 5.1 候補 A: EPUB3 出力（`book-epub`）

`output/<book>/` の markdown 群を XHTML に変換し、`nav.xhtml` と `content.opf` を添えて zip する。iPhone への導線は 2 通り:

1. **Send to Kindle → iOS Kindle アプリ**。Amazon は 2022 年以降 EPUB を受け付け、自身の形式に変換してライブラリへ配信する（[マイナビニュース](https://news.mynavi.jp/article/20220503-2336836/)）。**現行の操作体験（E1〜E7）をそのまま再利用できる点が最大の利点**
2. **AirDrop / iCloud Drive → Apple Books**。Amazon を経由しない

- 利点: 実装コストが最小。追加依存ほぼゼロ。E2/E3/E5/E6/E7 を既存アプリのまま獲得。UR-6（目で読む・grep）も損なわない。PDF が巨大で扱えない問題の別解にもなる
- 欠点: E8（画面 OFF 継続）は解決しない。Send to Kindle 経由だとライブラリに購入書籍と別エントリで並ぶ
- リスク: Send to Kindle 経由の personal document で画面読み上げ／自動ページ送りが効くかは要検証（§8 V-2）

### 5.2 候補 B: 単一 HTML / プレーンテキスト出力

`<book>.md` を 1 枚の HTML に変換して iCloud Drive 経由で参照し、Safari + 画面読み上げで聞く。

- 利点: 最小実装（数十行）
- 欠点: 位置の保持なし（E3 欠落）。14 万字を 1 枚の HTML にすると実用に耐えない。目次なし
- 評価: **EPUB とほぼ同じ手間で体験が明確に劣る**。EPUB を作るなら不要

### 5.3 候補 C: TTS で音声ファイル化（`book-tts` → M4B）

正規化テキストを TTS にかけ、章ごとの音声を結合してチャプター付き M4B を生成する。Apple Books または BookPlayer 等の専用アプリで再生。

- 利点: **E8 を本質的に解決**（画面 OFF・バックグラウンド・ロック画面/AirPods 操作・車載）。再生位置の保持と速度変更はプレイヤ側の標準機能。「ながら聞き」という新しい体験を得る
- 欠点: 生成時間とストレージ。テキスト修正のたび再生成。検索・ハイライト不可（E6 欠落）。目と耳の切替が断絶（E5 欠落）。転送が必要（数百 MB）
- 論点: 外部 API を使うなら**書籍全文を第三者に送信する**ことになる（§10）
- 補足: EPUB（候補 A）と**排他ではなく併用**が自然。目で読む／検索する需要は EPUB、ながら聞きは M4B

### 5.4 候補 D: EPUB3 Media Overlays（音声 + テキスト同期）

音声とテキストを SMIL で同期させ、読み上げ位置がハイライトされる形式。

- 利点: E5（目と耳の切替）と E8 を同時に満たす理想形
- 欠点: **対応リーダーが実質限られる**。Kindle は非対応。文単位の音声分割とタイムスタンプ生成が必要で生成コストが跳ね上がる
- 評価: **非ゴールとする**。理想だが個人ツールの投資対効果に合わない

### 5.5 候補 E: 現状維持 + 運用手順の文書化

`output/` を iCloud Drive に置き、iOS のファイルアプリ + 画面読み上げで markdown を聞く運用を README に書くだけ。

- 利点: 実装ゼロ
- 欠点: §3 のほぼ全課題が残る。特にテキスト品質層（P3-1, P3-2）が未解決なので実用性が低い
- 評価: 検証用のベースラインとしてのみ有用。**まずこれを 1 冊試して不満点を実測する**のは Phase 0 として妥当

## 7. 推奨アーキテクチャと段階導入

### 7.1 共通の中間層を置く

§3.3 で述べたとおり、正規化は形式選択と独立している。既存の `exporters/` パターンに素直に乗る:

```text
output/<book>/                     ← 既存。再 OCR なしで何度でも変換できる
  page_NNN.png
  index.json
  <book>.md
  pages/page_NNN.md
        │
        ▼
  book_ocr/speech/normalize.py     ← 新規。P3-1〜P3-5 を解決する純粋関数群
        │  ページ跨ぎ結合 / markdown 記法除去 / 表・図の方針適用 / ノイズ除去
        ▼
  speech.json（正規化済みテキスト）  ← FR-10。人が確認・修正できる中間成果物
        │
        ├──► exporters/epub.py  ──► <book>.epub   （Phase 1）
        └──► tts/*.py           ──► <book>.m4b    （Phase 3）
```

この形にすると:

- 正規化ロジックが 1 箇所にまとまり、`mypy --strict` + mock なしの純粋関数テストが書ける（CONTRIBUTING の方針どおり）
- 中間ファイルを挟むことで、**OCR に 1 時間かけ直さずに**出力を作り直せる。TTS のように課金が絡む工程では特に重要
- TTS エンジンは `OCREngine` Protocol と同じパターンで差し替え可能にする（FR-14）

### 7.2 コマンド構成

`kindle-cap-pdf` が既存 PNG から PDF を再生成するのと同じ思想で、既存の出力ディレクトリを入力に取る独立コマンドとする。

```bash
uv run book-epub output/my-book/            # → output/my-book/my-book.epub
uv run book-tts  output/my-book/            # → output/my-book/my-book.m4b
```

`&&` 連結の放置運用（UR-4）もそのまま維持できる:

```bash
uv run kindle-cap --name my-book --pages 200 --auto-direction \
  && uv run book-ocr output/my-book/ \
  && uv run book-epub output/my-book/
```

### 7.3 段階導入

| Phase | 内容 | 得られるもの | 目安 |
|---|---|---|---|
| **0** | §8 の前提検証。特に V-1 / V-4 / V-6。候補 E を 1 冊試す | 優先度の確定。**ここで C の優先度が上下する** | 数時間 |
| **1** | 正規化（FR-6, FR-7, FR-9）+ EPUB3 出力（FR-1〜FR-5） | UR-1〜UR-7 を既存アプリのまま獲得 | 小 |
| **2** | 章構造の推定（FR-3 強化）、表・図の方針（FR-8）、読み辞書（FR-15） | 目次の実用化、聞きやすさ改善 | 中 |
| **3** | TTS + M4B（FR-11〜FR-14） | UR-8（ながら聞き）の獲得 | 中〜大 |

> [!NOTE]
> Phase 1 に**最小限の正規化を含める**のが要点。FR-6（ページ跨ぎ結合）と FR-7（markdown 記法除去）を欠いた EPUB は、markdown を読み上げるのと大差がない。ここを削って「まず EPUB だけ」とやると、Phase 1 の価値がほぼ消える。

### 7.4 章構造の推定方針（Phase 2 の設計論点）

現状 `<!-- page:NNN -->` しか構造情報がない。候補:

1. 1 ページ = 1 セクション。目次は 200 項目になり実用性は低いが、頭出しの粒度としては機能する（**Phase 1 の既定として妥当**）
2. yomitoku が出力した markdown 見出し（`#`）を採用する。**認識精度は要検証（§8 V-4）**
3. N ページごとに機械的に区切る（例: 10 ページ = 1 セクション）
4. 巻頭の目次ページの OCR 結果から章題を抽出し、本文中の一致箇所を探す。精度は高いが実装は重い
5. LLM に章構造を推定させる。このリポジトリは Claude Code 前提の運用なので相性は良いが、本体機能に組み込むかは別判断

推奨: Phase 1 は 1 + 2 のハイブリッド（見出しがあれば使い、なければページ単位）。4/5 は Phase 2 以降の検討。

なお、章単位のファイル分割は目次のためだけでなく、**巨大な単一 XHTML を避けるという技術的要請**でもある。

## 8. 検証すべき前提（Phase 0）

要求分析の段階で決め打ちできない事項。いずれも短時間で潰せる。

| ID | 検証項目 | 方法 | 何が変わるか |
|---|---|---|---|
| **V-1** | iOS の「画面の読み上げ」は画面ロック／スリープ中に継続するか | 手持ちのリフロー本で実機確認 | **最重要**。継続しないなら UR-8 が Must に昇格し、候補 C（M4B）の優先度が Phase 3 → Phase 1.5 に上がる |
| V-2 | Send to Kindle で送った personal document (EPUB) が iOS Kindle アプリで読み上げ対象になり、自動ページ送りが効くか | 任意の DRM フリー EPUB を 1 冊送って確認 | 候補 A の前提。崩れると Apple Books ルートに切り替え |
| V-3 | Send to Kindle のファイルサイズ上限 | 公式ドキュメント確認 | 画像なしテキスト EPUB なら数 MB のはずで、問題になる可能性は低い |
| V-4 | yomitoku の md 出力に見出し (`#`) がどの程度含まれるか | `grep -c '^#' output/*/pages/*.md` | 章構造推定の実現可能性（§7.4 の案 2） |
| V-5 | 表 (`\|`) / 画像参照 (`![`) の混入率 | 同上 | FR-8 の方針決定。混入が少なければ単純除去で足りる |
| V-6 | ページ跨ぎ文の頻度（末尾が句点で終わらないページの割合） | 既存 md をスクリプトで集計 | FR-6 の実装優先度と結合ルールの設計 |
| V-7 | Apple Books に M4B を入れた場合のチャプター／再開位置／速度の挙動 | サンプル M4B で確認 | 専用アプリ（BookPlayer 等）を前提にすべきかの判断 |
| V-8 | macOS `say -v Kyoko` の音質が実用に耐えるか | 30 秒サンプルを生成して聞く | NFR-2（ローカル完結を既定）が現実的かどうか。耐えないなら外部 API 前提となり §10 の論点が重くなる |

V-4〜V-6 は既存の `output/` に対する集計だけで済み、**実装判断に直結する割に数分で終わる**。ここから着手するのが効率的。

## 9. コスト試算（Phase 3 の判断材料）

前提（すべて概算・要実測）:

- Kindle for Mac ウィンドウ 1 画面 ≒ 500〜900 字（和書・標準フォント）
- 200 ページ ≒ **10〜18 万字**
- 日本語 TTS の標準話速 ≒ 320〜400 字/分 → **音声長 4.5〜9.5 時間**（1.5 倍速なら 3〜6 時間）

15 万字・音声 7 時間を仮定した場合:

| 方式 | 費用 | 品質 | 備考 |
|---|---|---|---|
| macOS `say`（Kyoko 等） | **無料・オフライン** | 低〜中 | 生成はリアルタイムより高速。V-8 で判断 |
| OpenAI TTS 標準 | 約 $2〜3 | 中〜高 | $15 / 100 万文字 |
| OpenAI TTS HD | 約 $4〜5 | 高 | $30 / 100 万文字 |
| Gemini Flash TTS | 約 $12〜13（バッチ半額） | 高 | 音声出力トークン課金（$20 / 100 万トークン、25 トークン/秒） |

- ファイルサイズ: AAC 64 kbps モノラルで 7 時間 ≒ **約 200 MB**。既存の PNG 群（数 GB）や PDF（100 MB〜1 GB）と比べれば軽い
- 1 冊あたり数百円という水準は、**個人の読書 1 冊分としては十分許容範囲**と考えられる

> [!NOTE]
> 価格は 2026 年 7 月時点の公開情報にもとづく概算であり、実装前に再確認すること。日本語の文字／トークンカウント方法は提供元によって異なる点にも注意。

## 10. リスクと方針

### 10.1 書籍全文の外部送信

外部 TTS API を使うと、購入書籍の全文が第三者のサーバへ送信される。README の方針（個人利用・購入済み書籍を自分の別環境に流すだけ）と緊張関係にある。

方針案:

- **既定はローカル TTS（`say`）とし、オフラインで完結させる**（NFR-2）
- 外部 API は `--tts-engine openai` 等の**明示的 opt-in** とし、実行時に「書籍全文が外部送信される」旨を警告する（NFR-3）
- API キーは環境変数からのみ受け取り、`index.json` 等の成果物に残さない

### 10.2 OCR 誤字が音声では補正できない

P3-6。目で読めば無視できる誤字が、音声では意味不明な発話になる。読み上げ品質の下限を決めるのは OCR 精度であり、形式変換では改善しない。

- 現実的な緩和: FR-15（読み辞書）で固有名詞の誤読・誤字を後段で補正する
- 将来候補: 正規化段階で LLM に文脈校正させる（§11）

### 10.3 音声生成のやり直しコスト

テキストを 1 文字直すたびに 7 時間分を再生成するのは非現実的。

- FR-13（章単位の再開・スキップ）を最初から設計に入れる。既存 `--skip-existing` と同じ思想
- 正規化テキスト（`speech.json`）を成果物として残し、そこを直してから章単位で再生成できるようにする

### 10.4 スコープの膨張

TTS・章構造推定・LLM 校正はいずれも単体で 1 プロジェクトになりうる。

- Phase 1（正規化 + EPUB）で一度リリースし、実際に 1 冊聞いてから Phase 2 以降を決める
- §4.4 の非ゴールを守る
